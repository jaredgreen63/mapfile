# CLAUDE.md

This file provides guidance to Claude Code (claude.com/claude-code) when working with this repository.

## What this repository is

This is a **data-only repository** used to store custom map files for the game **Rust** (Facepunch Studios). There is no source code, build system, test suite, or CI configuration — the repository exists to host and version large binary `.map` files, which are typically uploaded through the GitHub web UI ("Add files via upload" commits) and served to Rust dedicated servers via raw download URLs.

## Repository contents

| File | Size | Notes |
|------|------|-------|
| `RustECustommap.map` | ~18.6 MB | Contains RustEdit custom monument data (`CustomMonumentData` XML, custom topology layers) |
| `newmap.map` | ~18.5 MB | Contains a `buildingblocks` data section |
| `newmap2.map` | ~18.5 MB | Similar to `RustECustommap.map` (RustEdit custom monument data) |

All three maps are roughly the same size, suggesting the same world size (likely iterations of the same or similar maps).

## The `.map` file format

These are binary Rust world files, **not** text files. Do not open, diff, or edit them as text.

Structure (as observed in these files):
- Bytes 0–3: little-endian `int32` format version (`0x0A` = version 10 in all three files).
- Remainder: LZ4-compressed Protobuf `WorldSerialization` payload containing terrain maps (height, splat, biome, topology, alpha, water), prefab placements, and paths.
- Editor extensions (from **RustEdit**) are embedded as named data sections; visible markers in these files include `CustomMonumentData` XML blocks, `buildingblocks`, `custom_topology_1`, `topology_layer_lookup`, and an `underwater` section tagged `1806`.

To inspect a map file without corrupting it, use binary-safe tools only:

```bash
od -A x -t x1z file.map | head        # hex dump of the header
strings -n 8 file.map | sort -u       # find embedded section names / XML markers
stat -c %s file.map                   # file size
```

The first 4 bytes should always decode to the expected version integer; a mismatch or a size wildly different from ~18 MB is a sign of a truncated or corrupted upload.

## Working conventions

- **Never modify `.map` files in this repo directly.** Maps are authored and edited externally in RustEdit (or generated by a Rust server) and the resulting file is committed whole. Any byte-level edit made here will corrupt the map.
- **Treat files as replace-only.** A map update means replacing the entire file with a newly exported version, committed with a message describing what changed in the map.
- **Preserve filenames.** Rust servers reference these maps by URL (e.g. a raw GitHub URL used as the server's `levelurl`). Renaming or deleting a file breaks any server pointing at it — confirm with the user before doing either.
- **Watch repository size.** Each committed revision of an ~18 MB binary adds to git history permanently. If frequent map updates are expected, suggest Git LFS rather than silently growing the repo.
- **Line-ending / text tooling hazards.** Do not run formatters, `sed`, or anything that could apply text transformations (CRLF conversion, trailing-newline fixes) to `.map` files. If a `.gitattributes` is ever added, `*.map binary` is the correct entry.

## Git workflow

- Default branch: `main`.
- History consists of whole-file uploads; there are no meaningful diffs to review between commits — compare file sizes and embedded strings instead if you need to characterize a change.
- No hooks, no CI: nothing runs on push.

## What Claude Code can usefully do here

- Verify map file integrity (header version, size sanity checks).
- Extract metadata (embedded RustEdit section names, XML monument data markers) using binary-safe tooling.
- Manage repository hygiene: `.gitattributes`, README, Git LFS migration if asked.
- Answer questions about the Rust map format and how these files are consumed by Rust servers.

There is nothing to build, lint, or test in this repository.
